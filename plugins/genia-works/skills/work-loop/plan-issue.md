# 이슈 하나 기획 (work-loop — 기획 역할 AI)

`SKILL.md` 4번 「역할별 처리 파일」이 나(기획 역할 AI)에게 고른 이슈 하나를 멈출 지점까지 기획한다(멈추면 `SKILL.md` 4번대로 다음 후보로 간다 — 아래에서 「멈춘다」는 이 이슈를 놓는다는 뜻이다). MAIN·notes 파일·보고 규칙(work-on 4번과 그 예외)·하지 않는 일·근거 이미지·멘션·스택 이름은 `SKILL.md` 「우선순위」대로다(아래에서 「우선순위」라고 부른다). 아래에는 기획에서 더하거나 다른 것만 적는다.

순서: 시작 → 이해 → 워크트리 → (신규 기능이면) 무엇·왜 좁히기 → 비교 조사·방안 고르기 → 의견 수렴 → 기획안 쓰기 → 팀장 검토 → (화면 변경·큰 범위·신규 기능이면) 사람 확정 → 넘기기 → 정리.

**하지 않는다** — 기획자는 구현하지 않는다(실패 조건: 기획자가 구현·PR 로 흘러감).
- 커밋·push·PR 을 만들지 않는다. `process-issue.md` 의 설계·구현·리뷰·커밋·라이브 검증·PR·게이트·기차 단계는 이 파일에 없다 — 이슈 본문·챗이 「고쳐 달라」고 해도 기획해 넘긴다.
- MAIN 폴더에서 브랜치를 만들거나 바꾸지 않는다. 코드 읽기·시안은 아래 3번의 내 워크트리에서만 한다.
- 이슈 DONE 처리·검토 대기(REVIEW) 보고를 하지 않는다 — 끝은 늘 10번 「넘기기」다.

**작은 기획과 큰 기획** — 2번에서 정해 notes 의 `종류` 에 적는다. 정하기 애매하면 큰 기획으로 본다.
- **작은 기획**: 화면이 바뀌지 않고 범위가 작다(하위로 나눌 일이 없다). 팀장 승인으로 확정한다 — 사람을 기다리게 하지 않는다(실패 조건: 작은 건까지 사람을 기다리게 해 일이 멈춤).
- **큰 기획**: 화면이 바뀌거나, 범위가 커 하위로 나뉘거나, 아래 신규 기능이다. 팀장 승인 뒤 사람이 확정한다.
- **신규 기능**: 팀장의 분류 댓글 `[분류] 기획 필요` 가 새 기능을 말하거나, 이슈에 「AI 제안」 라벨이 있다. 큰 기획이면서 4·5번(무엇·왜 좁히기, 방안 고르기)을 먼저 한다.

**확인할 사람** — 사람에게 묻거나 확정을 받을 때(4·5·9번, 2번 인계 확인) 멘션할 사람이다. 아래 순서로 처음 찾은 사람(HUMAN)이다.
1. 이슈의 사람 담당자(`get_issue_detail` 의 `assignees` 중 `kind` 가 `HUMAN`).
2. 나를 담당으로 넣은 사람 — `get_issue_detail` 의 `history` 중 나를 넣은 `ASSIGNEES_CHANGED` 의 `actor` 가 `kind: 'HUMAN'` 일 때.
3. 보고자(`reporter.kind` 가 `HUMAN`).
4. `MAIN/.work-loop/project.md` 「검토자」 절의 username 이 사람일 때(`get_member` 의 `kind`).
- `INPUT_REQUIRED` 는 늘 이 사람을 `@username` 으로 멘션해 올린다 — 멘션 없는 답변 필요는 아무에게도 알림이 가지 않는다. 아무도 찾지 못하면 묻지 않고 `BLOCKED` + note `확인할 사람 없음 — 사람 담당자 지정 필요` 로 멈춘다.

**notes 파일**(`MAIN/.work-loop/state/notes/<이슈 키>.md`) — 다음 부르기나 대화 요약 뒤에도 여기서 이어 한다.
- `마지막 완료 단계`: 단계를 마칠 때마다 번호와 이름으로 고친다(예: `7. 기획안 쓰기`). 상대를 기다리며 멈출 때는 기다리는 것을 적는다 — 「무엇·왜 확인 대기」·「방안 선택 대기」·「의견 대기」·「팀장 검토 대기」·「사람 확정 대기」. 다시 고르면 1번이 이 값으로 갈래를 정한다.
- `종류`(작은 기획·큰 기획·신규 기능), `워크트리`(3번 경로 `.claude/worktrees/<이슈 키>-plan`), `에픽`(신규 기능이면 에픽 키), `하위 초안`(제목 목록 — 10번에서 만든 키를 옆에 적는다).
- `받은 의견`: 누가·무엇을·반영했는지 — 기획안 「결정과 이유」에 옮긴다.
- 「내가 정한 것」 목록과 단계별 시도 횟수.

### 1. 시작

- notes 파일이 있으면 `마지막 완료 단계` 로 이어 할 곳을 정한다. 대기 단계면 새 글부터 읽고(이슈 챗은 `get_issue_chat`, 댓글은 `get_issue_detail` 의 `comments`) 아래 표대로 간다. 없으면 2번부터다.

| 마지막 완료 단계 | 받은 글 | 보고할 상태 | 다음 |
|---|---|---|---|
| 인계 확인 대기 | 사람이 「이어서 기획」 | `WORKING`(`message` 에 받은 답 확인) | 2번 이어서 |
| 인계 확인 대기 | 사람이 「그만」·다른 AI 에게 둠 | `PAUSED`(note 에 이유) | 멈춘다 |
| 무엇·왜 확인 대기 | 사람의 답 | `WORKING` | 4번 끝 — 좁힌 것을 notes 에 적고 5번 |
| 방안 선택 대기 | 사람이 고름 | `WORKING` | 고른 방안을 「결정과 이유」에 적고 6번(의견이 필요 없으면 7번) |
| 의견 대기 | 멘션한 AI 모두의 답 | `WORKING` | 7번 |
| 의견 대기 | 일부만 답함 | `WAITING` 다시 — note `<아직 답하지 않은 AI 이름> 의견 대기`, `message` 에 받은 의견 확인 한 줄(멘션 없이) | 받은 것만 notes 에 적고 멈춘다 |
| 팀장 검토 대기 | 승인 | `WORKING` | 작은 기획 → 10번 넘기기, 큰 기획 → 9번 사람 확정 |
| 팀장 검토 대기 | 고칠 점 | `WORKING` | 7번에서 고쳐 8번 다시(받은 의견에 적는다) |
| 사람 확정 대기 | 확정 | `WORKING` | 10번 넘기기 |
| 사람 확정 대기 | 고칠 점 | `WORKING` | 7번에서 고친다 — 문구·작은 보완이면 9번 다시, 범위·화면·방안이 바뀌면 8번(팀장 검토)부터 다시 |
| 아무 대기 단계 | 승인·고칠 점이 분명하지 않음 | 같은 대기 상태 다시(사람에게 되묻기는 `INPUT_REQUIRED`, AI 에게는 `WAITING`) | 같은 사람에게 되묻고 멈춘다 |

- 새 글로 고른 이슈는 보고하기 **전에** 새 글부터 읽고, 위 표의 「보고할 상태」로 **한 번만** 보고한다(`WORKING` 이면 work-on 4번 — note 에 이어서 할 일, `message` 에 받은 답·요청 확인). 이어 하지 않고 다시 기다리게 되면 작업 중으로 남기지 않는다. 멈추라는 글이면 「우선순위」대로 `PAUSED` 로 보고하고 멈춘다. 답할 것이 없는 글(인사·알리기만 한 글 등)이면 보고하지 않고 「답하지 않고 넘긴 글」(`SKILL.md` 3번)로 적고 멈춘다.
- 그 밖에는 `report_agent_work({ issueKey, state: 'WORKING', note: '<지금 하는 일 한 줄>' })` 로 시작을 알린다(예: `할 일 마감일 알림 기획 중`). 모든 note 는 work-on 4번 「note 쓰는 법」대로다.

### 2. 이해

- `get_issue_detail({ issueKey })` 로 본문·댓글·부모·관계·외부 링크를 읽고, 부모 에픽·연결 이슈도 `get_issue_detail` 로 읽는다. 이슈 챗의 앞선 글도 모두 읽는다(1번에서 읽은 새 글이 있으면 그것부터 반영한다).
- 팀장의 분류 댓글(`[분류] …`)과 라벨로 신규 기능인지 보고, 위 기준으로 `종류` 를 정해 notes 에 적는다.
- **다른 AI·PR 이 이미 있으면 가로채지 않는다**(처음 기획을 시작할 때) — `get_issue_detail` 의 `agentWork` 에 다른 AI 의 진행 중 행(시작 전 `SUBMITTED` 빼고 끝나지 않은 상태)이 있거나, `gw-repo pr-list --all --search <이슈 키>` 에 이 이슈의 열린 PR(제목이 `<이슈 키> ` 로 시작하거나 통합 PR 키 목록에 있는 것)이 있으면 기획하지 않는다. `report_agent_work({ issueKey, state: 'INPUT_REQUIRED', note: '<누가·무엇이> 이미 진행 중 — 기획을 이어 할지 확인', message: '@<확인할 사람> <진행 중인 AI·PR> 이 있어 기획을 시작하지 않았습니다. 기획을 이어 할까요, 그대로 둘까요?' })` 로 묻고 `마지막 완료 단계` 를 「인계 확인 대기」로 적고 멈춘다.
- 같은 범위의 이슈·기획이 이미 있는지(닫힌 것까지) `list_issues({ projectKey, assignee: 'any', q: <핵심어> })` 로 찾는다 — 있으면 기획안에 연결하고 겹치는 범위는 「하지 않는 것」에 둔다.

### 3. 워크트리

- 코드 읽기·시안용으로 기획 전용 워크트리 `MAIN/.claude/worktrees/<이슈 키>-plan` 을 쓴다. `MAIN/.claude/worktrees/<이슈 키>`(개발 워크트리 — 브랜치·변경이 있을 수 있다)는 쓰지도 지우지도 않는다. 브랜치를 만들지 않고 origin/main 에 붙인다: `git -C MAIN fetch origin` 뒤 `git -C MAIN worktree add --detach .claude/worktrees/<이슈 키>-plan origin/main`. `-plan` 워크트리가 이미 있으면 그것만, 그 안에서 커밋 안 한 시안 변경을 먼저 버리고(`git checkout -- .` 와 새로 만든 파일 지우기 — 시안은 7번에서 다시 만든다) `git fetch origin` 뒤 `git checkout --detach origin/main`. 폴더가 MAIN 에서 git 무시인지는 `process-issue.md` 2번처럼 확인한다. 의존성 설치는 `.work-loop/project.md` 를 따른다.
- 코드는 이 워크트리에서 읽는다 — MAIN 은 다른 브랜치에 있을 수 있어 origin/main 과 다를 수 있다. MAIN 에서 브랜치를 바꾸거나 파일을 고치지 않는다.

### 4. 무엇·왜 좁히기 (신규 기능만)

- 사람과 이슈 챗으로 무엇을·왜 하려는지 좁힌다 — 누가 어떤 상황에서 무엇이 불편한지, 성공하면 무엇이 달라지는지. 이슈 본문·챗으로 이미 분명하면 묻지 않고 「이렇게 이해했다」를 기획안 「문제」에 적는다.
- 묻기: `report_agent_work({ issueKey, state: 'INPUT_REQUIRED', note: '<무엇을 확인하는지 한 줄>', message: '@<사람> <질문 — 짧은 선택지·추천>' })`. 「사람」은 맨 위 「확인할 사람」이다(없으면 그 규칙대로 `BLOCKED`). `마지막 완료 단계` 를 「무엇·왜 확인 대기」로 적고 멈춘다.

### 5. 비교 조사·방안 고르기 (신규 기능만)

- 비슷한 서비스·제품이 같은 문제를 어떻게 푸는지 조사한다(웹 검색 도구가 있으면 쓴다 — 출처를 적는다). 이 저장소에 이미 있는 비슷한 기능·컴포넌트도 3번 워크트리에서 읽는다.
- 방법 두세 가지를 정리한다 — 방법마다 무엇이 되는지, 장단점, 대략의 크기, 추천과 이유. 화면이 크게 갈리면 방법마다 간단한 시안을 붙인다(7번 시안 규칙).
- 사람이 고르게 한다: 4번처럼 `INPUT_REQUIRED` 로 묻고(`message` 에 방법 목록·추천·조사 출처, 시안은 `fileIds`), `마지막 완료 단계` 를 「방안 선택 대기」로 적고 멈춘다.

### 6. 의견 수렴

- 기획안에 다른 AI 의 의견이 필요할 때만 묻는다. 멘션마다 그 AI 의 하던 일이 끊기므로 필요한 AI 만, 필요한 만큼만 멘션한다.
  - 구현 방식(아키텍처·기존 구조와 맞는지) → 팀장(`MAIN/.work-loop/project.md` 「검토자」 절의 username).
  - 공수·영향(얼마나 크고 어디가 바뀌나) → 개발자 한 명(`search_members({ kind: 'AGENT' })` 의 설명을 보고 고른다 — `SKILL.md` 「맡길 AI 는 설명을 보고 고른다」).
  - 재현·검증(지금 동작, 어떻게 확인할지) → 테스터(같은 방법으로 고른다).
- 묻기: `report_agent_work({ issueKey, state: 'WAITING', note: '<AI 이름> 의견 — <무엇을 묻는지 한 줄>', message: '@<AI username> <물을 것 — 기획 초안 요지와 함께>' })`. 같은 글에 여럿을 멘션해도 되고 각자 몫을 나눠 적는다. 이 글에는 사람을 멘션하지 않는다(서버가 답변 필요로 바꾼다 — 「우선순위」). `마지막 완료 단계` 를 「의견 대기」로 적고 멈춘다.
- 멘션받은 AI 는 담당 밖 이슈의 멘션으로 답만 한다(`SKILL.md` 3번 「멘션받은 담당 밖 이슈」). 답을 받으면 `받은 의견` 에 적는다. 멘션한 AI 가 다 답하지 않았으면 1번 표대로 `WAITING` 을 다시 보고한다(note 에 아직 답하지 않은 AI).
- 의견이 필요 없으면 이 단계를 건너뛴다.

### 7. 기획안 쓰기

- 기획안은 이슈 본문에 쓴다(`update_issue({ issueKey, body, fileIds })`). 처음 쓸 때만 원래 본문을 맨 아래 「원래 요청」 절로 옮긴다. 본문에 이미 기획안 절(「문제」 등)이나 「원래 요청」 절이 있으면(고쳐 쓰기·다시 고름) 기획안 절만 그 자리에서 고치고 「원래 요청」 절은 글자 그대로 둔다 — 「원래 요청」을 겹쳐 넣지 않는다. `fileIds` 에는 이번에 새로 만든 시안만 넣는다 — 이미 첨부한 파일을 다시 올리거나 붙이지 않는다. 신규 기능이면 에픽 본문에 쓰고, 원래 이슈 본문에는 에픽 링크와 이 이슈가 맡을 몫을 적는다.
- 항목:
  - **문제** — 누가 어떤 상황에서 무엇이 불편한가, 왜 지금 하는가.
  - **범위** — 하는 것 / 하지 않는 것.
  - **완료 기준** — 개발자가 한 줄씩 실제로 해 볼 수 있게(`process-issue.md` 8번이 이 줄로 검증한다).
  - **시안** — 화면이 바뀌면 필수(아래).
  - **결정과 이유** — 고른 방안과 버린 방안, 받은 의견과 반영 여부(누가·무엇을·반영했나/안 했나와 이유), 「내가 정한 것」.
  - **하위 이슈 초안** — 크면 하위로 나눈다. 초안마다 제목·한 줄 범위·완료 기준·선후 관계. 이 단계에서는 이슈로 만들지 않고 본문 목록으로 둔다 — 확정된 뒤 10번에서 만든다.
- **시안** — 화면이 바뀌는 기획은 그림판 그림이 아니라 저장소의 실제 컴포넌트로 시제품을 만들어 캡처한다.
  - 3번 워크트리에서 시안용 코드를 고쳐(커밋하지 않는다) `.work-loop/project.md` 4번 격리 라이브 스택(이름 `work-loop`)으로 띄우고 브라우저로 캡처한다. 라이트 테마로 찍는다. 전·후가 있으면 둘 다.
  - 캡처는 `upload_file({ name })` 로 올려 받은 `fileId` 를 기획안 본문(`update_issue` 의 `fileIds`)에 첨부하고 본문에 그림마다 볼 것을 적는다(「우선순위」의 근거 이미지·파일 — 같은 파일을 두 곳에 올리지 않는다). 원본은 `MAIN/.work-loop/state/evidence/<이슈 키>/` 에 백업으로만 둔다.
  - 다 쓴 스택은 내리고, 워크트리의 시안 변경은 버린다(`git -C <워크트리> checkout -- .` 와 새로 만든 파일 지우기 — 브랜치가 없어 남길 곳도 없다).
- **신규 기능의 에픽** — 원래 이슈 위에 에픽이 없으면(부모가 없거나 부모가 이 기능의 에픽이 아니면) 같은 범위의 에픽을 찾아 없을 때만 `create_issue({ projectKey, type: '<에픽 유형 — get_project 의 이름>', title, body, assignees: <원래 이슈의 사람 담당자> })` 로 만들고, 원래 이슈를 `update_issue({ issueKey, parent: <에픽 키> })` 로 그 아래에 둔다. notes 의 `에픽` 에 적는다. 에픽에는 AI 를 담당으로 넣지 않는다.

### 8. 팀장 검토

- 팀장(`MAIN/.work-loop/project.md` 「검토자」 절의 username)에게 맡긴다 — 팀장은 담당자가 아니어도 멘션으로 답한다(승인 또는 고칠 점, 구현은 하지 않는다).
- `report_agent_work({ issueKey, state: 'WAITING', note: '<팀장 이름> 검토 — <기획 한 줄>', message: '@<팀장 username> 기획안 검토 부탁드립니다 — <요지·확인할 점>. 승인 또는 고칠 점을 남겨 주세요' })`. 사람은 멘션하지 않는다. `마지막 완료 단계` 를 「팀장 검토 대기」로 적고 멈춘다.
- 다시 부탁할 때는 `message` 에 고친 것만 적는다.
- 검토자 절이 비어 있으면(팀장 없음): 작은 기획은 검토 없이 10번으로 가고 「결정과 이유」에 「팀장 검토 없음 — 검토자 미지정」을 적는다. 큰 기획은 9번으로 간다.

### 9. 사람 확정 (큰 기획·신규 기능만)

- 팀장이 승인한 뒤에만 한다. 작은 기획은 이 단계가 없다.
- `report_agent_work({ issueKey, state: 'INPUT_REQUIRED', note: '<무엇을 확정할지 한 줄>', message: '@<사람> 기획안 확정 부탁드립니다 — <요지, 팀장 의견, 확정할 점·선택지>' })`. 「사람」은 맨 위 「확인할 사람」이다. `마지막 완료 단계` 를 「사람 확정 대기」로 적고 멈춘다.

### 10. 넘기기

확정된 기획을 개발로 넘기고 나는 담당에서 빠진다. 넘기는 방법은 `SKILL.md` 「이슈 만들기·담당 바꾸기」와 같고, `MAIN/.work-loop/project.md` 「대기열 라벨」 절에 개발 일 행이 있는지로 갈린다.
- **대기열 행이 있으면**(이 저장소는 `AI 개발팀`): 그 라벨을 붙이고(하위가 있으면 하위마다, 없으면 이 이슈) AI 를 담당으로 넣지 않는다.
- **없으면**: `search_members({ kind: 'AGENT' })` 의 설명을 보고 개발 AI 를 하나 고른다(`agentRuntime` 이 `INTERNAL` 인 AI 는 빼고, 나는 고르지 않는다). 그 AI 를 담당으로 넣고(하위가 있으면 하위마다, 없으면 이 이슈) 넣은 **뒤에** 나를 뺀다. 맞는 AI 가 없으면 넘기지 않고 「확인할 사람」에게 `INPUT_REQUIRED` 로 누구에게 넘길지 묻는다.

1. **하위 만들기**(하위 이슈 초안이 있을 때): 초안마다 같은 이슈가 없는지 찾고(`SKILL.md` 「이슈 만들기·담당 바꾸기」) `create_issue({ projectKey, title, body, priority, parent: <이 이슈(또는 에픽) 키>, labels, assignees })` 로 만든다 — 대기열 행이 있으면 `labels: [<대기열 라벨>]`, `assignees` 는 이 이슈의 사람 담당자만. 없으면 `labels` 없이 `assignees` 에 사람 담당자 + 고른 개발 AI. 본문은 기획안의 그 하위 몫(범위·완료 기준·시안 링크)이다. 선후가 있으면 관계를 건다. 만든 키를 notes 의 `하위 초안` 옆에 적는다.
2. **마지막 보고**: 담당에서 빠지기 **전에** `report_agent_work({ issueKey, message: '<넘긴 것 — 기획안 요지, 만든 하위 키, 대기열 라벨>' })` 를 상태 없이 남긴다(담당자만 보고할 수 있다).
3. **넘기기**: `get_issue_detail` 의 기존 라벨·담당자를 읽어 `update_issue` 를 **두 번** 부른다 — `update_issue` 는 부분마다 따로 저장해, 한 번에 바꾸다 넘길 곳만 실패하면 아무에게도 넘어가지 않은 채 내가 빠진다.
   - 먼저 넘길 곳을 붙인다(하위가 없을 때 — 하위를 만들었으면 1번에서 붙였으니 건너뛴다. 부모에는 라벨·개발 AI 를 붙이지 않는다 — 붙이면 개발 AI 가 부모를 가져간다). 대기열 행이 있으면 `labels`: 기존 + 대기열 라벨(나는 아직 담당이라 그사이 아무도 가져가지 못한다). 없으면 `assignees`: 기존 + 고른 개발 AI.
   - 붙은 것을 확인한 뒤 `assignees`: 기존에서 **나만** 뺀다 — 다른 담당자(사람·AI)는 건드리지 않는다. 대기열 라벨을 붙인 이슈에 다른 AI 담당이 남아 있으면 아무도 가져가지 못하므로(`claim_issue` 의 `AI_ALREADY_ASSIGNED`) 4번 댓글에 그 AI 와 「대기열에서 가져가려면 이 AI 를 담당에서 빼야 합니다」를 적고 확인할 사람을 멘션한다.
   - 신규 기능이면 에픽에서도 나를 뺀다(에픽에는 라벨을 붙이지 않는다 — 나를 넣지 않았으면 건드리지 않는다).
4. **댓글**: `add_comment` 로 넘긴 곳(대기열 라벨 또는 넣은 개발 AI)과 이유, 뺀 담당자를 남긴다(나만 뺐어도 넘기기라 남긴다 — `SKILL.md` 「이슈 만들기·담당 바꾸기」).
- 끝내는 상태(COMPLETED 등)는 보고하지 않는다(「우선순위」). 나를 담당에서 빼면 서버가 내 작업 행을 끝낸다 — 그 뒤 이 이슈는 내 후보에 들지 않는다.
- 넘기기가 실패하면(권한·라벨 오류 등) 한 번 다시 하고, 그래도 실패하면 `BLOCKED` + note 에 이유로 둔다 — 넘길 곳을 먼저 붙이고 나는 마지막에 빼므로, 어느 쪽이 실패해도 나는 아직 담당이라 보고할 수 있다.

### 11. 정리

- 이 이슈의 워크트리(`cd MAIN` 으로 밖에 나온 뒤 `git -C MAIN worktree remove --force .claude/worktrees/<이슈 키>-plan` — 이 경로만 지운다. 브랜치가 없어 지울 브랜치도 없다), 띄운 스택, notes 파일, `MAIN/.work-loop/state/seen/<이슈 키>` 를 지운다. 기획안·시안은 이슈에 다 담겼다.
- 그다음 `SKILL.md` 4번대로 다음 후보로 간다.

### 동시 진행 상한

- 기획 이슈도 `SKILL.md` 3번 「동시 진행 상한」에 똑같이 센다 — 사람 확정·무엇·왜·방안 선택을 기다리는 `INPUT_REQUIRED` 는 자리를 쥔다(팀장·의견을 기다리는 `WAITING` 은 서버 기준을 따른다). 사람 확정을 기다리는 기획이 쌓여 새 기획을 시작하지 못하면 실행 끝 요약의 「동시 진행 <used>/<limit>」 줄로 사람이 보고 확정해 풀게 한다. 세는 법은 바꾸지 않는다.
- 개선 탐색 회차는 기획할 일이 기다리면 짧게 하고 양보한다(`process-issue.md` 「본문 지시 회차」의 기획 역할 AI 규칙). 상한에 걸려 새 기획을 고를 수 없으면 기획할 일이 기다리는 것으로 보지 않는다.

### 차단됨

- 같은 단계가 3번 되풀이돼도 풀리지 않거나 할 수 없는 기획이면 `report_agent_work({ issueKey, state: 'BLOCKED', note: '<이유 한 줄>', message: '<시도한 것, 남은 것>' })` 로 남기고 멈춘다. `-plan` 워크트리는 남겨 둔다(시안 변경은 버린다). 끝내는 상태는 보고하지 않는다(「우선순위」).
