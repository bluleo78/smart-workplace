# 릴리스 노트 작성 가이드

저장소 루트 `releases/<버전>.md` 가 앱 사용자 메뉴 「새 소식」에 그대로 나간다(web 빌드에 번들, WP-439). GitLab Release 에도 링크된다.
이 가이드는 `releases/` 밖에 둔다 — 그 폴더는 통째로 web 빌드 입력이라 다른 파일을 두면 번들에 들어가고 web 이미지가 다시 빌드된다.
릴리스 절차(버전 정하기·커밋·태그)는 `/release` 스킬(`.claude/skills/release/SKILL.md`)과 `docs/ops/release.md` 를 따르고, **노트의 형식과 문장은 이 문서가 기준**이다.

## 독자

팀원과 고객사 사용자. 개발 용어를 모르는 사람이 「이번 업데이트로 내가 무엇을 할 수 있게 됐나」를 읽는 글이다.

## 파일

- 이름: `releases/<x.y.z>.md` — 태그 `vX.Y.Z` 의 버전과 같게. **`releases/` 에는 이 노트 파일 말고 아무것도 두지 않는다** — 앱은 `0.9.0-rc.1.md` 같은 프리릴리스 이름도 노트로 읽어 「새 소식」에 띄울 수 있다(초안은 다른 곳에서 쓴다).
- 맨 앞 frontmatter(`---` 사이, 한 줄에 `키: 값`):

| 키 | 필수 | 값 |
|---|---|---|
| `version` | ✓ | 파일명과 같은 버전 |
| `date` | ✓ | 태그 찍는 날(KST) `YYYY-MM-DD` — 「새 소식」에 표시된다 |
| `range` | | `/release prepare` 의 plan 결과 그대로(`v0.8.0..1acdc9e21e29`) — 어떤 커밋까지 담았는지 기록 |
| `hidden` | | 정확히 `true`(소문자)면 「새 소식」 목록과 안 읽음 점에서 빠진다. 보일 때는 줄을 쓰지 않는다(`True`·`yes` 는 검사에서 거부된다) |

- 본문: 마크다운. `##` 제목(영역) 아래 `-` 목록(항목)만 쓴다. 표·이미지·링크·코드 블록은 쓰지 않는다(숨김 노트만 예외 — 아래).
- 검사: `node deploy/release/prepare.mjs check-note releases/<버전>.md --base-version <기준 버전>` — **파일명과 머리 정보(version·date·range·hidden)만** 검사한다. 본문 규칙은 검사하지 않으므로 사람이 확정할 때 본다. GitLab 파이프라인은 태그 커밋에 이 파일이 없으면 멈춘다.

## 영역(`##` 제목)

- 사용자가 보는 **앱 메뉴 이름**으로 묶는다 — 홈·이슈·메일·드라이브·노트·채팅·캘린더·AI·설정 등. 여러 메뉴에 걸친 변경은 `드라이브·메일` 처럼 가운뎃점으로 잇는다.
- 메뉴가 아니라 기능 하나가 새로 생긴 경우는 그 기능 이름을 쓴다(예: `새 소식`).
- 순서: 이번 릴리스에서 새로 할 수 있게 된 것 → 바뀐 것 → 고친 것.
- 이 릴리스보다 먼저(같은 날이라도 이 버전 반영 전에) 운영에 나가 있던 기능을 노트에서 처음 소개할 때는 제목 끝에 `(M월 D일부터 제공 중)` 을 붙인다 — 「새로 생겼다」로 오해하지 않게. 0.9.0 의 문서 미리보기가 그 예다(릴리스 체계 전환 전 10월 17일 오전에 먼저 배포).

## 항목 문장

- 한 항목 = 한 줄, 「무엇을 할 수 있게 됐는지」를 사용자 말투로: `~할 수 있습니다`, `~합니다`, `~보여 줍니다`.
  - 좋음: `- 메일에 첨부된 한글·오피스 문서도 바로 열어 볼 수 있습니다.`
  - 나쁨: `- converter 서비스로 HWP→PDF 변환 지원(WP-432)` — 기술 이름·이슈 키·개조식.
- 버그 수정은 사용자가 겪던 증상 기준으로: `- 드라이브에서 이름을 바꾼 뒤 목록이 갱신되지 않던 문제를 고쳤습니다.`
- 사용자가 미리 알아야 할 제약은 같은 항목에 짧게 덧붙인다: `처음 열 때는 변환하느라 몇 초 걸릴 수 있습니다.`
- 문장 끝에 마침표. 화면에 나오는 이름은 화면 표기 그대로 「」 로 감싼다(예: 사용자 메뉴의 「새 소식」).

## 넣지 않는 것

- 이슈 키(WP-123), 커밋·버전 비교, 사람 이름
- 기술 이름 — Helm·컨테이너·이미지·converter·마이그레이션·API 경로·라이브러리 이름
- 테스트·리팩터·CI·문서·배포 도구 변경, 사용자가 알아챌 수 없는 내부 수정
- 보안 취약점의 세부 내용(「보안을 강화했습니다」 정도로만)

## 사용자에게 보이는 변경이 없을 때

노트는 그래도 만든다(태그 파이프라인이 파일을 요구한다). 숨김으로 두고, 본문은 영역 제목 없이 아래 한 줄만 쓴다(앱에 보이지 않으므로 「##/-」 규칙의 예외):

```markdown
---
version: 0.9.1
date: 2026-10-24
range: v0.9.0..abcdef012345
hidden: true
---

사용자에게 보이는 변경 없음
```

## 예시 — `0.9.0.md`

```markdown
---
version: 0.9.0
date: 2026-10-17
range: v0.8.0..1acdc9e21e29
---

## 새 소식
- 사용자 메뉴의 「새 소식」에서 업데이트마다 달라진 점을 볼 수 있습니다. 아직 읽지 않은 소식이 있으면 프로필 사진과 메뉴에 점이 표시됩니다.
- 사용자 메뉴에서 지금 쓰고 있는 버전을 확인할 수 있습니다.

## 드라이브·메일 (10월 17일부터 제공 중)
- 한글(HWP·HWPX)·파워포인트·워드 문서를 내려받지 않고 원래 모양 그대로 바로 미리볼 수 있습니다. 엑셀(XLS)은 시트 표로 보여 줍니다.
```

## 쓰는 순서

1. `/release prepare` 의 plan 결과에서 이슈 목록을 받는다.
2. 이슈마다 **이슈 제목·본문을 읽고** 쓴다(커밋 제목을 옮겨 적지 않는다). 내부 변경으로 분류된 이슈도 사용자 체감 변경이 정말 없는지 훑어본다.
3. 초안을 사람에게 보여 주고 **버전과 문장을 확정받는다.**
4. 태그를 찍은 뒤에는 노트를 고치지 않는다 — 이미 그 버전 빌드에 들어갔다. 고칠 내용은 다음 버전 노트에 쓴다.
5. 핫픽스 노트는 main 에도 옮긴다(다음 main 릴리스의 「새 소식」에 빠지지 않게).
