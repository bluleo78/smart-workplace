# PWA · Web Push 실기기 스모크

자동화(E2E)로 검증할 수 없는 실제 푸시 서비스(Apple·Google·Mozilla) 경유 수신과 OS 알림 표시를 기기별로 확인한다.

## 전제

- HTTPS로 접근 가능한 서버(스테이징 또는 운영). `workplace.push.enabled=true`.
- 서버에서 외부 푸시 서비스로 아웃바운드 연결 가능(`web.push.apple.com`, `fcm.googleapis.com`, `updates.push.services.mozilla.com`).
- VAPID 공개 키·비공개 키 모두 설정됨 (`WORKPLACE_PUSH_VAPID_PUBLIC`, `WORKPLACE_PUSH_VAPID_PRIVATE` 환경 변수 또는 둘 다 없어서 자동 생성 DB 키).
- **VAPID 연락처 `WORKPLACE_PUSH_SUBJECT` 에 실제 주소 설정**(예: `mailto:admin@회사도메인`). 미설정 시 기본값 `mailto:admin@localhost` 는 FCM 은 통과하지만 Apple(`web.push.apple.com`)이 거부해 **iPhone·iPad·Safari 만 알림이 오지 않는다**(WP-152). 잘못된 값이면 API 기동 로그에 `[push] VAPID subject ... ` 경고가 남는다.
- 폐쇄망이면 `workplace.push.enabled=false` 설정 후 설정 화면에 "푸시 알림을 사용할 수 없습니다" 메시지가 정상 표시되는 것으로 검증.
- 테스트 계정 2개(A: 수신자, B: 발신자), 두 계정이 같은 테넌트의 같은 채널 멤버. A는 두 번째 테넌트에도 소속.

## 대상 환경

| 환경 | 설치 방법 |
|---|---|
| iPhone (iOS 16.4+) Safari | 공유 → 홈 화면에 추가 → 홈 화면 아이콘으로 실행 |
| iPad (iPadOS 16.4+) Safari | 위와 동일 |
| Android Chrome | 메뉴 → 앱 설치(또는 브라우저 그대로) |
| 데스크톱 Chrome / Edge | 주소창 설치 아이콘(또는 브라우저 그대로) |
| macOS Safari 16+ | 파일 → Dock에 추가(또는 브라우저 그대로) |

## 절차 (환경마다 반복)

### 1. 설정 페이지에서 푸시 활성화 및 권한 허용

- [ ] A로 로그인 → `/settings/notifications` (설정 > 알림) 접근
- [ ] "이 기기에서 푸시 받기" 토글 ON → OS 권한 요청 팝업 출현 및 허용
  - 테스트ID: `push-device-toggle`
  - 토글 활성화 후 OS 알림 권한 상태 확인(브라우저 주소창에 알림 아이콘 또는 OS 설정)

### 2. iOS 전용: 설치 상태 및 토글 비활성 확인

- [ ] Safari 탭에서 설정 > 알림을 열면 "iPhone·iPad에서는 홈 화면에 추가한 앱에서만 알림을 받을 수 있습니다" 안내가 표시
  - 테스트ID: `push-ios-install-guide`
- [ ] 토글이 비활성(회색)인지 확인(브라우저 탭에서는 설치 필수)
- [ ] 홈 화면 앱으로 다시 진입 후 토글이 활성화되는지 확인

### 3. 앱 완전 종료

- [ ] 앱(또는 탭)을 **완전히 종료** — 백그라운드 프로세스도 제거

### 4. DM 알림 수신 확인

- [ ] B가 A에게 DM 전송
- [ ] A 기기에 "B 이름 / 메시지 미리보기" 시스템 알림이 표시되는지 확인
  - **예상 결과:** 실제 푸시 서비스 경유 시스템 알림 표시(Android Chrome, 데스크톱 Chrome/Edge, iOS 홈화면 PWA)
  - ⚠️ iOS Safari 탭에서는 푸시 구독 불가(홈 화면 설치 필수)

### 5. 채널 멘션 알림 수신 확인

- [ ] B가 채널에서 A를 @mention
- [ ] A 기기에 "#채널명 · B 이름" 시스템 알림이 표시되는지 확인

### 6. 이슈 배정 알림 수신 확인

- [ ] B가 이슈를 A에게 배정
- [ ] A 기기에 "KEY-N 제목 / B님이 회원님을 배정했습니다" 시스템 알림이 표시되는지 확인

### 7. 캘린더 초대 알림 수신 확인

- [ ] B가 A를 일정(캘린더 이벤트)에 초대
- [ ] A 기기에 "일정 제목 / B님이 일정에 초대했습니다" 시스템 알림이 표시되는지 확인

### 8. 동일 DM 연속 수신 및 태그 교체 확인

- [ ] B가 같은 DM에 연속 3건 전송
- [ ] 각 알림의 표시 방식 기록:
  - Android/데스크톱: 알림 센터에서 이전 알림과 **태그로 교체**되는지, 다시 울리는지(renotify)
  - iOS: 각각 별도로 표시되는지, 중복 제거 여부 기록
- [ ] 사운드·진동·배너 동작 확인

### 9. 알림 탭(터치) → 앱 포커스 및 화면 이동 (앱 열어 둔 상태)

- [ ] **앱 창을 열어 둔 상태** (다른 탭 활성이어도 상관없음)
- [ ] 알림을 탭하면:
  - **해당 앱 윈도우로 포커스** → 목적지로 이동
- [ ] 이동 확인:
  - DM 알림 → `/chat/dms/:id` (DM 화면)
  - 채널 멘션 → `/chat/channels/:id?thread=<threadId>` (스레드 포함)
  - 이슈 배정 → `/projects/:key/issues/:number` (이슈 상세)
  - 캘린더 초대 → `/calendar?eventId=<eventId>` (캘린더 화면에서 해당 일정 포커스)

### 10. 알림 탭 → 앱 없는 상태 (새 창 열기)

- [ ] **앱을 완전히 종료** (모든 창 닫기)
- [ ] B가 A에게 DM 전송
- [ ] A 기기에 알림 수신
- [ ] A가 알림을 탭하면:
  - 앱이 새 창으로 실행 → `/push-open` 진입점 거친 후 목적지로 자동 이동
  - `/chat/dms/:id` (DM 화면)으로 이동 확인

### 11. 비앱 페이지 창 열린 상태에서 알림 탭 (회귀 위험)

- [ ] **A가 로그인 상태에서** B가 A에게 DM 전송 → 알림 수신 후 OS 트레이에 남김
- [ ] **A가 로그아웃** (서버 구독 매핑 삭제, 하지만 OS 트레이의 알림은 유지)
- [ ] **로그아웃 후 `/login` 페이지 탭이 유일하게 열려있는 상태**
- [ ] A가 OS 트레이에 남아있는 알림을 탭하면:
  - **예상 결과** — `/login` 창은 "앱 라우트"가 아니므로(로그인 화면은 postMessage 를 받을 라우터가 없음) 서비스워커가 그 창을 `/push-open?to=..&t=..` 로 `navigate()` 시킨 뒤 포커스한다. `/push-open` 진입점이 미로그인 상태를 감지해 목적지를 `sessionStorage` 의 `pendingPushTarget` 에 저장하고 `/login` 으로 리다이렉트 — 이후 로그인하면 저장된 목적지(`/chat/dms/:id` 등)로 자동 이동(12번 시나리오와 동일 경로로 합류)
  - **실제 결과 ____** (기기에서 기록)

### 12. 로그인 중 수신한 알림 탭 후 로그아웃 → 로그인 → 목적지 도달

- [ ] **A가 로그인 상태에서** B가 A에게 DM 전송
- [ ] A 기기에 알림 수신 후 OS 트레이에 남김 (앱은 닫은 상태)
- [ ] **A가 로그아웃** (서버 구독 매핑 삭제, OS 트레이의 알림은 유지)
- [ ] **A가 OS 트레이에 남아있는 알림을 탭하면:**
  - 앱이 새 창으로 열림 → `/push-open` 진입점 거침
  - 미로그인이므로 알림 목적지를 `sessionStorage`의 `pendingPushTarget`에 저장
  - `/login` 페이지로 리다이렉트
  - A가 로그인하면 → AppLayout 진입 시 저장된 목적지(`/chat/dms/:id` 등)로 자동 이동 확인
- [ ] **다른 테넌트 알림의 경우:**
  - 로그인 중 수신한 다른 테넌트 DM → OS 트레이 → 로그아웃 → 탭
  - `/push-open?to=...&t=<tenantId>` → pendingPushTarget 저장
  - 로그인 후 목적지로 이동하면서 **해당 테넌트로 자동 전환** 확인

### 13. 테넌트 전환 및 알림 탭

- [ ] A가 두 번째 테넌트를 보고 있는 상태
- [ ] B(같은 첫 번째 테넌트)가 DM 전송
- [ ] A가 알림을 탭하면:
  - **첫 번째 테넌트로 자동 전환**
  - DM 화면(`/chat/dms/:id`)으로 이동
  - 테스트ID 또는 동작 확인: 테넌트 전환 후 채널/DM 목록이 첫 번째 테넌트 것으로 갱신

### 14. 현재 화면 보기 중 푸시 억제 (OS 별 차이)

**알림 억제 정책**: DM·채널 멘션(MENTION)만 억제 대상이며, 그마저도 **경로(pathname)와 쿼리(search)가 완전히 같은 화면**을 보고 있을 때만 서비스워커가 알림 표시 대신 앱에 메시지를 포스트한다. 이슈(ISSUE)·캘린더(CALENDAR) 알림은 절대 억제하지 않는다(캘린더는 `?eventId=` 로 서로 다른 일정을 구분해야 하고, 이슈 경로는 테넌트 간 key 충돌 가능성이 있어 pathname 일치만으로는 "같은 화면"을 보장할 수 없다). 단, Safari/iOS는 무알림 푸시가 반복되면 구독이 취소되므로 **항상 알림 표시**.

- [ ] A가 앱을 열어 특정 DM을 보고 있는 중 (`/chat/dms/:id` 경로)
- [ ] B가 같은 DM에 새 메시지 전송
- [ ] **그룹 1: Android Chrome / 데스크톱 Chrome·Edge (suppressible browsers)**
  - [ ] 알림이 **뜨지 않음**(억제됨), 화면에만 새 메시지 표시
  - [ ] DM 목록의 메시지 카운트·배지 갱신 확인
- [ ] **그룹 2: iOS 홈 화면 PWA / macOS Safari (always-visible browsers)**
  - [ ] 알림이 **여전히 표시**(항상 가시화, requiresVisibleNotification=true)
- [ ] **이슈/캘린더는 절대 억제되지 않음 확인:** A가 이슈 상세(`/projects/:key/issues/:number`) 또는 캘린더(`/calendar?eventId=<id>`)의 바로 그 화면을 보고 있는 중에도 B가 같은 이슈/일정에 변경을 가하면 **알림이 항상 표시**되는지 확인(억제 가능 브라우저에서도)

### 14-1. 채널 스레드 패턴: 채널 메인 화면 보기 중 스레드 멘션 억제

- [ ] A가 앱을 열어 채널의 **메인 메시지 목록** (`/chat/channels/:id` — 쿼리 파라미터 없음)을 보고 있는 중
- [ ] B가 같은 채널의 메시지를 멘션 (알림 대상은 `/chat/channels/:id?thread=<threadId>`)
- [ ] **예상 결과:** (억제 가능 브라우저에서)
  - 경로 정합성 검사가 pathname **및 쿼리(search)까지** 완전히 같아야 억제하므로, 대상(`?thread=<threadId>`)과 현재 보고 있는 화면(쿼리 없음)의 쿼리가 달라 **억제되지 않고 알림이 표시될 것으로 예상**(round 2 수정 — 이전에는 pathname만 비교해 오억제됨)
  - **실제 결과 ____** (기기에서 기록)

### 15. 알림 종류 설정 끄기 → 알림 미수신

- [ ] 설정 > 알림 → "캘린더" 토글 OFF
  - 테스트ID: `push-pref-CALENDAR`
- [ ] B가 A를 새 일정에 초대
- [ ] A 기기에 캘린더 알림이 **오지 않는지** 확인
- [ ] 다른 종류(DM, 채널 멘션, 이슈)는 여전히 오는지 확인
- [ ] 설정 > 알림 → 각 종류별 토글:
  - "다이렉트 메시지": `push-pref-DM`
  - "채널 멘션": `push-pref-MENTION`
  - "이슈": `push-pref-ISSUE`
  - "캘린더": `push-pref-CALENDAR`

### 16. 로그아웃 후 푸시 미수신

- [ ] A가 로그아웃
- [ ] B가 DM 전송
- [ ] A 기기에 알림이 **오지 않는지** 확인
- [ ] A가 로그인 후 알림이 다시 오는지 확인

### 17. 업데이트 토스트 및 새 버전 반영

- [ ] 서버에 새 버전 배포
- [ ] 앱을 닫았다가 다시 진입
- [ ] "새 버전이 있습니다" 또는 유사 토스트 메시지 표시 확인
  - 토스트: 앱 홈 페이지 상단 또는 공지 영역에서 자동 표시 또는 강제 새로고침 안내
- [ ] 새로고침 시 최신 버전 로드 확인(리소스 캐시 갱신)

## 알려진 제약

- **iOS/iPadOS**: 홈 화면에 설치한 앱에서만 푸시 수신. 알림 액션 버튼 없음. Safari 탭에서는 푸시 구독 불가.
- **Android**: 배터리 최적화로 지연될 수 있음(수 초~수 분). 설정 > 배터리 > 배터리 최적화 > 앱을 "배터리 최적화 제외" 목록에 추가 권장.
- **데스크톱 Chrome/Edge**: OS 알림 권한이 필요. OS 설정 또는 브라우저 주소창 사이트 설정에서 알림 허용 필요.
- **macOS Safari**: Dock에 추가한 앱 또는 브라우저 탭에서 알림 가능. 시스템 설정 > 알림에서 Safari(또는 설치한 웹 앱) 알림 허용 필요.
- **폐쇄망** (`workplace.push.enabled=false`): 
  - 설정 화면에 "푸시 알림을 사용할 수 없습니다" 메시지 표시(정상)
  - 테스트ID: `push-disabled-notice`
  - 아웃바운드 HTTPS 불가 시 푸시 서비스로 전달 불가 → 알림 미도착(설계)
- **VAPID 키**: 환경 변수 `WORKPLACE_PUSH_VAPID_PUBLIC` + `WORKPLACE_PUSH_VAPID_PRIVATE` 둘 다 설정되거나 둘 다 미설정이어야 함(이 경우 DB에서 자동 생성). 한쪽만 설정되면 환경 변수는 무시되고 DB 키가 대신 사용됨. 푸시 on/off는 `workplace.push.enabled` 값으로만 결정.
- **발송 실패 추적**: 푸시 서비스가 거부하면 API 로그에 발송 1회당 host·status 별 1줄로 `[push] 발송 실패 host=... status=... count=... reason=...` 가 남는다(네트워크 오류는 status=-1, 만료 404/410 은 기록 안 함). 구독별 연속 실패는 `push_subscription.failure_count`(5회면 구독 삭제), 성공은 `last_success_at` 로 확인.
