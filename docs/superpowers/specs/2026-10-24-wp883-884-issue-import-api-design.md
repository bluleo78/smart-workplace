# 이슈 가져오기 API — 원작성자·원시각 보존, 알림 억제 (WP-883, WP-884)

에픽 WP-882 「Jira 프로젝트 이관 지원」 웨이브 2. VOC WPV-24·WPV-25(보고자 문규임, 2026-10-23).

## 왜

Jira CLIM(이슈 316건·댓글 1,229개·첨부 498개)을 Works 로 옮기려 한다. 이관은 사용자 쪽 스크립트가 Jira REST 를 읽어 Works REST 를 개인 API 토큰(`swp_`)으로 부르는 방식이다. 지금 API 로 옮기면:

- 보고자·댓글 작성자가 모두 스크립트 실행자로, 생성 시각이 모두 이관 시각으로 남는다. 누가 언제 보고·검증했는지가 QA 근거라 이대로는 쓸 수 없다(WP-883).
- 담당자 지정·댓글마다 인박스 알림·웹 푸시가 나가 12명에게 약 1,500건(1인 최대 약 370건)이 쏟아지고, AI 담당 이슈는 AI 작업이 자동으로 시작된다(WP-884).

## 사용자가 정한 것

- **별도 가져오기 API** 를 둔다. 일반 이슈·댓글 API 에는 작성자·시각·알림 끄기 필드를 더하지 않는다.
- **워크스페이스 관리자(테넌트 ADMIN 역할)만** 쓸 수 있다. 프로젝트 소유자는 쓸 수 없다 — 남의 이름으로 기록을 남기는 기능이라 프로젝트 권한보다 위에서 허락한다. 누구나 프로젝트를 만들면 소유자가 되므로 소유자까지 열면 사실상 모든 사용자에게 열린다.
- 함께 넣는다: **이슈 번호 지정**, **워처 지정**, **변경 이력 가져오기**.
- Jira 를 읽고 사용자를 맞추는 일은 스크립트 몫이다. 서버가 Jira 에 직접 붙는 가져오기(화면·연동)는 만들지 않는다.

## 목표 / 하지 않을 것

목표
- 가져온 이슈·댓글·첨부·이력이 원래 사람·원래 시각으로 남고, 상세·활동 목록·생성일 정렬·필터가 그 시각 기준으로 동작한다.
- 가져오기는 인박스 알림·웹 푸시·AI 착수를 만들지 않는다. 가져온 뒤의 일반 변경은 평소대로 알린다.
- 일반 사용자 토큰(관리자 아님, 프로젝트 소유자 포함)으로는 작성자·시각을 정할 수 없다.

하지 않을 것
- 가져오기 화면, Jira 연동, 사용자 매핑 화면, 진행 표시.
- MCP 도구(스크립트는 REST 를 부른다).
- 이미 있는 이슈에 댓글만 덧붙이는 「추가 가져오기」 — 이슈 한 건을 한 번에 넣는다.
- 이슈 관계(차단 의존·관련·중복 등)·외부 링크 — WP-887(웨이브 3)에서 관계 유형과 함께 가져오기 경로를 만든다. 일반 의존성 API 로 넣으면 관리자·지금 시각 이력이 남으므로 이관 스크립트는 웨이브 3 를 기다린다.
- 수정·영향 버전 — WP-888(웨이브 4).
- 아래 「변경 이력」 표 밖의 이력 종류(사이클·스프린트 이동, 버전, 구성요소, 링크, 본문 변경 등), 작업 기록·투표·반응.
- 「가져옴」 표시 UI — 이번엔 데이터·감사 로그로만 남긴다(후속 후보).

실패로 보는 것(기술적으로 동작해도)
- 가져오기 한 번으로 누구에게든 알림·푸시가 한 건이라도 가는 것.
- 관리자가 아닌 사람이 이 API 로 남의 이름을 쓸 수 있는 것.
- 요청 일부만 저장되고 나머지는 실패해 어중간한 이슈가 남는 것.

## API

`POST /api/v1/projects/{projectKey}/import/issues` — 이슈 한 건(댓글·첨부·워처·이력 포함)을 한 트랜잭션으로 넣는다. 성공 201 + 만든 이슈(`IssueResponse` 와 같은 모양).

### 권한
- 호출자가 이 테넌트의 ADMIN 역할(`PermissionChecker.userHasRole(callerId, "ADMIN")`)이 아니면 403. 프로젝트 OWNER 도 403.
- 사람 신원만(JWT·개인 토큰). AI 키(`ak_`)·AI 구성원 호출은 403.
- PERSONAL 프로젝트로는 가져오지 않는다(400) — ADMIN 우회가 개인 프로젝트에는 없다.

### 요청 본문 `ImportIssueRequest`
| 필드 | 필수 | 설명 |
|---|---|---|
| `number` | 선택 | 이슈 번호(1 ~ 1,000,000,000). 주면 그 번호로 만들고, 이미 있으면 409. 없으면 평소처럼 다음 번호. 번호와 원본 키가 함께 겹치면 원본 키 409 가 먼저다. |
| `sourceKey` | 선택 | 원본 키(예: `CLIM-17`, 100자). 이슈에 저장·감사 로그에 남긴다. 프로젝트 안에서 고유 — 같은 원본 키를 다시 가져오면 409(시간 초과 뒤 재시도가 이슈를 두 번 만들지 않게). |
| `title`, `body` | 제목 필수 | 일반 생성과 같은 상한(제목 200, 본문 50,000). |
| `typeId`, `statusId`/`status`, `priority`, `startDate`, `dueDate`, `parentNumber`, `milestoneId`, `labelIds`, `labelNames`, `cycleIds` | 선택 | 일반 생성(`CreateIssueRequest`)과 같은 뜻·검증. |
| `fields` | 선택 | 커스텀 필드 값 — 이름 → 값(일반 필드 값 API 와 같은 형식·검증). 이력 행은 남기지 않는다. |
| `reporter` | 필수 | 보고자 username. |
| `assignees` | 선택 | 담당자 username 목록(50명). |
| `watchers` | 선택 | 워처 username 목록 — **넘긴 목록 그대로**만 워처가 된다. 일반 생성과 달리 보고자·담당자를 자동으로 넣지 않는다(CLIM 은 담당자가 워처가 아닌 이슈가 44건 — 자동으로 넣으면 원본과 달라지고 이관 뒤 그 사람들에게 알림이 간다). |
| `createdAt` | 필수 | 원래 생성 시각(오프셋 포함 ISO-8601). |
| `updatedAt` | 선택 | 원래 수정 시각. 없으면 `createdAt`. `createdAt` 보다 이르면 400. |
| `closedAt` | 선택 | 종료 범주(완료·취소) 상태일 때만. 없으면 `updatedAt`. 종료가 아닌데 주면 400. (CLIM 은 Jira 가 `RND DONE` 을 완료 범주로 쳐서 Jira 의 종료 시각이 승인 시각이 아니다 — 스크립트는 Works 에서 완료 범주로 매핑한 상태로 들어간 마지막 전이 시각을 넘긴다. `resolutiondate` 는 4건에만 있어 쓰지 않는다.) |
| `attachments` | 선택 | `[{fileId, attachedBy, attachedAt}]` — `fileId` 는 호출자가 기존 스테이징 업로드로 먼저 올린 파일. 이슈당 50개까지(CLIM 최대 13). |
| `comments` | 선택 | `[{author, createdAt, updatedAt?, body}]` — 입력 순서대로. 본문 50,000자, 500개까지. |
| `history` | 선택 | 변경 이력 — 아래. 1,000개까지(CLIM 최대 약 41). |

본문·댓글의 이미지는 호출자가 기존 본문 이미지 업로드(`POST .../issues/body-images` 계열)로 먼저 올리고 글에 그 참조를 넣는다. 가져오기가 연결하면서 올린 사람을 그 글의 작성자(본문=보고자, 댓글=댓글 작성자)로, 올린 시각을 그 글의 작성 시각으로 바꾼다.

### 변경 이력 `history[]`
`{type, actor, at, from?, to?, added?, removed?}` — `actor` 는 username, `at` 은 원래 시각. Works 에 이미 있는 이력 종류만 받고, 저장 모양은 일반 변경이 남기는 행과 같게 만든다(활동 목록·홈 활동이 그대로 그린다).

| type | from / to | 저장 |
|---|---|---|
| `STATUS_CHANGED` | **Works 프로젝트 상태 id**(`fromStatusId`·`toStatusId`). 이 프로젝트 상태가 아니면 400 | 값은 그 상태의 지금 이름 |
| `PRIORITY_CHANGED` | 우선순위 코드(`HIGHEST`…`LOWEST`) | 코드 그대로 |
| `ASSIGNEES_CHANGED` | `added`·`removed` = username 목록 | 사람 요약(id·username·이름·종류) |
| `TITLE_CHANGED` | 문자열(200자) | 그대로 |
| `TYPE_CHANGED` | Works 프로젝트 유형 id(`fromTypeId`·`toTypeId`) | `{from:{id,name},to:{id,name}}` |
| `DUE_DATE_CHANGED`, `START_DATE_CHANGED` | 날짜(`YYYY-MM-DD`) 또는 null | 날짜 문자열 |
| `LABELS_CHANGED` | `added`·`removed` = 라벨 이름 목록. 이 프로젝트에 있는 라벨이어야 한다(없으면 400) | 라벨 요약 |

- 상태를 이름이 아니라 id 로 받는 이유: Jira 이력은 당시 이름을 남긴다. CLIM 은 같은 상태가 예전엔 `Resolved`, 지금은 `RND TEST` 이고, 이력은 영어(Open·Approved)·지금 이름은 한글(미해결·승인)이다. 이름을 그대로 받으면 QA 지표에서 한 상태가 둘로 쪼개진다 — 스크립트가 Jira 상태 id 로 Works 상태를 맞춰 넘긴다.
- 그 밖의 유형(사이클·스프린트 이동, 버전, 구성요소, 링크, 본문 변경 등)은 400. 사이클 변경은 Works 가 이력으로 남기지 않는 종류라 이번엔 받지 않는다(사용자 결정). 구성요소는 WP-933, 버전은 WP-888, 관계는 WP-887.
- 이력 행은 `at` 순서와 무관하게 받은 대로 넣는다 — 활동 목록이 시각으로 정렬한다.

### 사용자 해석
- 요청에 나온 모든 username(보고자·담당자·워처·댓글 작성자·첨부자·이력 행위자·이력의 added/removed)은 **그 프로젝트의 활성 구성원**이어야 한다. 하나라도 아니면 400 이고, 응답에 맞지 않은 username 을 모두 나열한다(스크립트가 한 번에 고치도록). 대체 사용자로 바꿔 넣지 않는다.
- CLIM 관련 사용자 14명은 모두 Works 에 있다 — 이관 전에 프로젝트 구성원으로 추가하면 된다.

## 저장 규칙

- 한 요청 = 한 트랜잭션. 어느 검증이든 실패하면 아무것도 남지 않는다.
- 이슈: `reporter_id` = 보고자, `created_at`·`updated_at`·`closed_at` = 요청 값. 번호를 지정했으면 프로젝트 번호 시퀀스를 `max(현재 다음 번호, number+1)` 로 올린다 — 이후 일반 생성이 겹치지 않게.
- 댓글: `author_id`·`created_at`·`updated_at` = 요청 값.
- 첨부: `attached_by`·`attached_at` = 요청 값. 첨부의 텍스트 추출 요청(`FileExtractionRequestedEvent`)은 평소처럼 낸다(알림이 아니라 AI 검색용).
- 담당자: `issue_assignee.assigned_by` = 호출자.
- 워처: `watchers` 만 이벤트 없이 바로 넣는다.
- 이력: `history[]` 만 원래 행위자·시각으로 넣는다. 가져오기 자체가 만드는 자동 이력(첨부 추가·담당자 지정)은 남기지 않는다 — 원래 이력과 섞여 가짜 행이 생긴다.
- 가져옴 표시: 이슈·댓글에 `imported_by`(호출자)·`imported_at`(지금), 이슈에 `import_source_key` 를 둔다(마이그레이션 V212, 모두 nullable 추가라 롤링 배포 호환). `(project_id, import_source_key)` 는 값이 있을 때 고유(부분 고유 인덱스).
- 감사 로그: 이슈마다 한 건 — `actionType = "ISSUE_IMPORTED"`, resource `issue`, resourceId 이슈 키, metadata `{sourceKey, reporter, comments, attachments, history}` 개수.

### 일반 생성과 다르게 푸는 검증 (원본을 그대로 옮기기 위해)
- 완료된 사이클에도 넣을 수 있다.
- 완료된 에픽 아래에 미완료 하위를 넣을 수 있다.
- 첨부 개수 상한은 이슈당 50(일반은 10, CLIM 최대 13). 파일 크기 상한은 일반과 같다.
- 가져온 뒤 일반 편집은 평소 규칙을 그대로 따른다.

## 부수 효과 — 무엇을 내고 무엇을 안 내나

가져오기는 아래를 **처음부터 일으키지 않는다**(플래그로 거르는 게 아니라 이벤트를 발행하지 않는다 — `@Async` 리스너에는 스레드 로컬 플래그가 전달되지 않는다).

| 안 냄 | 이유 |
|---|---|
| `IssueCreatedEvent`, `IssueAssignedEvent`, `IssueCommentedEvent`, 상태·우선순위 이벤트 | 인박스 알림·웹 푸시(알림 행 뒤에 따라 나감)·AI 에이전트 실행·AI 요약 재생성 |
| `agent_work` 시작 전 작업(`submitForAssignees`) | AI 담당자가 있어도 AI 작업을 만들지 않는다 |
| `WatcherAddedEvent`, `AgentToolWriteEvent`, `IssueHumanReplyPosted` | 채팅 스레드·AI 작업 자동 시작·재개 |

**내는 것**: 화면 갱신(`changeNotifier.created` 의 `ResourceChangedEvent`, SSE) 한 번, 첨부 텍스트 추출 요청, 감사 로그.

## 완료 조건과 검증

통합 테스트(JUnit, `IntegrationTestBase`)로 확인한다.
- ADMIN 이 아니면(프로젝트 OWNER 포함) 403, ADMIN 은 JWT·개인 토큰 모두 201. PERSONAL 프로젝트는 400.
- 가져온 이슈의 보고자·생성·수정·종료 시각, 댓글 작성자·시각, 첨부자·시각, 본문/댓글 이미지 올린 사람·시각, 이력 행위자·시각이 요청 값 그대로다. 이슈 목록 생성일 정렬이 원래 시각 순서다.
- 담당자·댓글·워처가 있는 가져오기 뒤 알림 행 0건, 푸시 요청 0건, AI 디스패치 0건, `agent_work` 0건.
- 가져온 이슈에 일반 API 로 댓글을 달면 평소대로 알림이 간다.
- 번호 지정: 지정 번호로 생성, 같은 번호 다시 가져오기 409, 이후 일반 생성은 겹치지 않는 번호.
- 구성원이 아닌 username 은 400 이고 모두 나열된다. 도중 실패 시 이슈·댓글·첨부가 남지 않는다.
- 감사 로그 한 건이 남는다.

스크립트 작성자용 사용법 문서를 함께 둔다(`docs/integrations/issue-import-api.md`): 순서(구성원·상태·유형·사이클·라벨·커스텀 필드 준비 → 이슈마다 첨부·이미지 스테이징 업로드 → 가져오기, 에픽 먼저), 요청 예시, 오류 응답. CLIM 실데이터 확인(2026-10-24)에서 나온 주의를 함께 적는다.
- 상태 이력은 Jira 상태 id → Works 상태 id 로 맞춘다(이름 금지). 종료 시각은 위 `closedAt` 설명대로.
- Jira 인라인 이미지는 이슈 첨부이기도 하다(약 345개) — 둘 다 올리면 이중으로 들어간다. 본문 이미지로 쓴 파일은 첨부로 다시 올리지 않는 식으로 한 번만 넣는다. 인라인 파일 카드(로그 등, 이미지 아님)는 첨부로 넣고 본문엔 링크 문구로.
- 대소문자만 다른 라벨(Compute/compute 등 6쌍)은 Works 에서 다른 라벨이 된다 — 미리 합친다.
- 다른 프로젝트(CL) 에픽이 부모인 62건은 `parentNumber` 로 걸 수 없다 — WP-887 외부 링크로.
- 본문의 `CLIM-n` 링크(773개)는 Works 프로젝트 키를 `CLIM` 으로 두면 번호 보존으로 그대로 맞는다.
- 커넥터가 주는 주석 HTML 을 그대로 보내면 5만 자를 넘는 댓글이 있다(CLIM-16·14) — 마크다운으로 바꿔 보낸다.
- 멘션은 Jira 계정 id → Works username 으로 바꾼다. 가져오기는 멘션 알림을 내지 않는다.
- 비밀값처럼 보이는 문자열(약 57곳)은 그대로 옮기면 Works 검색·첨부 텍스트 추출에도 들어간다 — 이관 전 검토.
- CLIM 일부 댓글(25개)은 이미 한 번 옮겨 온 것이라 본문 첫 줄에 「원작성자: …」가 있다 — 원래 사람으로 바꿀지는 스크립트가 정한다.

### 업로드 순서와 상한 (내가 정한 것)
- 본문 이미지는 한 사람이 한 프로젝트에 연결 전 50개까지·하루 뒤 수거, 스테이징 첨부는 24시간 뒤 사라진다. 상한·만료는 풀지 않는다.
- 그래서 스크립트는 **이슈마다 「그 이슈의 첨부·이미지 업로드 → 가져오기」를 번갈아** 한다. 이슈 한 건의 본문·댓글 이미지는 합쳐 50개까지 — 넘는 이슈가 실제로 나오면 그때 상한을 다시 본다.

## 만드는 쪽에 맡기는 것

- 구현 위치(새 `IssueImportService`·컨트롤러)와 기존 `planCreate`·저장소 메서드 재사용 방식 — 시각을 받는 저장소 오버로드가 필요하다.
- 본문 이미지 스테이징이 어느 이슈에도 아직 속하지 않은 상태에서 연결되는 방식(기존 `syncIssueImages` 를 호출자 기준으로 부른 뒤 소유·시각을 고쳐 쓰는 방법 등).
- 요청 크기: 본문 50,000자 × 댓글 500개까지 한 JSON 에 올 수 있다 — 서버 요청 크기 제한이 막지 않는지 확인.
