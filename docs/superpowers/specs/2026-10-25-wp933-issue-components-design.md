# WP-933 구성요소(Components) 설계

- 이슈: WP-933 「사용자로서 프로젝트를 담당 영역(구성요소)으로 나누고 이슈를 영역별로 걸러 보고 싶다」 (에픽 WP-882 Jira 이관, 웨이브 4)
- 작성: 2026-10-25
- 「(내 판단)」 표시는 대화에서 사용자가 정하지 않아 설계자가 정한 것이다.

## 1. 왜 만드는가

Jira CLIM 프로젝트는 이슈 317건 중 172건에 구성요소(Components) 12개를 쓰고, 그중 14건은 구성요소가 여러 개다. 12개 모두 「구성요소 리더」가 기본 담당자로 설정돼 있어, 담당자 없이 만든 이슈는 그 영역 리더가 자동으로 맡는다. Works 에는 같은 개념이 없다 — 라벨은 자유 태그라 「정해진 목록에서 고른다」는 성격이 없고, 다중 선택 커스텀 필드는 목록 필터가 되지 않는다.

이관 뒤에도 팀이 「Compute 일만 보기」, 「Compute 이슈는 soon.park 이 먼저 받는다」를 그대로 할 수 있게 한다.

## 2. 목표 · 비목표

**목표**
- 프로젝트별 구성요소 목록(이름·설명·담당자)을 프로젝트 설정에서 관리한다(추가·편집·보관·복원·삭제).
- 이슈에 구성요소를 여러 개 붙인다. 목록(보관 안 된 것)에 있는 값만 붙일 수 있다. 변경은 활동 기록에 남는다.
- 담당자 없이 만든 새 이슈에 구성요소 담당자를 자동 지정한다.
- 이슈 목록·보드·저장된 뷰·모바일에서 구성요소로 **걸러 본다**.
- MCP·AI 비서가 구성요소로 찾고, 붙이고, 목록을 읽는다.
- 가져오기 API(WP-883)가 구성요소와 그 변경 이력을 원본대로 넣는다.

**비목표**
- **구성요소로 묶어 보기(그룹)는 넣지 않는다** — 사용자 결정. 이슈에 여러 개가 붙으면 묶음이 겹치거나 숫자가 맞지 않아서다. 걸러 보기 + 저장된 뷰로 대신한다.
- 계층형 구성요소(Azure Area Path), 구성요소별 권한·알림 구독.
- AI 분류 제안(run-issue-classify-ai)이 구성요소를 추천하는 것.
- 라벨과 구성요소가 겹치는 CLIM 데이터(대소문자만 다른 Compute 라벨 등) 정리 — 이관 스크립트에서 한다.
- 개인 프로젝트 지원 — 혼자 쓰는 프로젝트라 영역 담당자가 의미 없다(내 판단). 서버는 개인 프로젝트에서 구성요소 생성을 400 으로 거부하고, 화면은 설정 섹션을 그리지 않는다.

**하면 실패인 것**
- 구성요소를 쓰지 않는 기존 프로젝트의 이슈 상세·만들기·필터 화면이 바뀐다(빈 칸·빈 필터가 생긴다).
- 사람이 고른 담당자가 구성요소 때문에 바뀐다.
- 가져오기로 옮긴 이슈의 담당자가 자동 지정으로 원본과 달라진다.

## 3. 데이터

새 마이그레이션 `V218__issue_components.sql` (머지 직전 main 번호와 다시 대조한다).

`project_component`
- `id`, `tenant_id`, `project_id` (FK project, cascade)
- `name VARCHAR(40)` — 프로젝트 안에서 대소문자 무시 유일(`UNIQUE (project_id, lower(name))`)
- `description VARCHAR(200)` null 가능
- `default_assignee_id` FK user, `ON DELETE SET NULL`, null 가능
- `archived_at TIMESTAMPTZ` null = 사용 중
- `created_by` FK user SET NULL, `created_at`, `updated_at`

`issue_component`
- PK `(issue_id, component_id)`, 두 FK 모두 cascade, `tenant_id`, `created_at`
- 인덱스 `(component_id)` — 필터용

두 표 모두 라벨처럼 `tenant_id` + 행 수준 보안 정책(V47·V48 방식)을 둔다.

**목록 순서**: 이름 오름차순(대소문자 무시). 설정·피커·필터·칩 모두 이 순서 — 「먼저 나오는 구성요소」의 기준이기도 하다(내 판단, 순서 끌기 없음).

## 4. 규칙

### 4.1 관리 권한
- 목록 보기: 프로젝트를 읽을 수 있는 사람.
- 추가·편집·보관·복원·삭제: **프로젝트 OWNER** 와 테넌트 ADMIN — 커스텀 필드·이슈 유형 관리와 같은 규칙을 따른다(내 판단). 자동 담당자 지정을 바꾸는 설정이라 라벨(멤버 누구나 생성)보다 좁힌다.
- 이슈에 붙이기·떼기: 라벨과 같은 워크플로 권한(멤버). **이슈를 만들 때도 구성원만 고를 수 있다** — 공개(OPEN) 프로젝트에서 구성원이 아닌 사람은 만들 때 구성요소를 넘기면 라벨·담당자와 같은 방식으로 거부되고(WP-477 규칙), 그 이슈는 구성요소 없이 들어와 자동 지정도 일어나지 않는다(사용자 결정 2026-10-25). 화면은 구성원이 아니면 만들기 창에 구성요소 칸을 그리지 않는다.

### 4.2 담당자(자동 지정)
- 구성요소마다 담당자 0~1명. 프로젝트 멤버이면서 활성 상태인 **사람**만 고를 수 있다(AI 구성원은 제외, 내 판단 — AI 를 담당자로 넣으면 작업이 바로 시작되는 부작용이 있다).
- 담당자가 나중에 프로젝트에서 빠지거나 비활성이 되면 값은 남기되 자동 지정은 건너뛴다. 설정 화면에 「프로젝트 구성원이 아님」 경고를 보여 준다.

### 4.3 자동 지정 시점
- 새 이슈를 **담당자 없이** 만들고 구성요소가 1개 이상일 때, 고른 구성요소를 목록 순서로 보아 처음으로 「유효한 담당자」가 있는 구성요소의 담당자 한 명을 붙인다.
- 화면·MCP·메일에서 만들기 등 일반 생성 경로 모두에 적용한다(`IssueService.create`). 가져오기(IMPORT 모드)는 적용하지 않는다.
- 이미 있는 이슈에 구성요소를 붙이거나 바꿔도 담당자는 바뀌지 않는다.
- 자동 지정도 일반 담당자 지정과 똑같이 알림·워처 등록·이벤트를 낸다.
- 활동 기록: 생성 때 `ASSIGNEES_CHANGED` 한 건을 남기고(지금은 생성 때 담당자 기록을 남기지 않으므로 자동 지정일 때만 남기는 새 기록이다) payload 에 `reason: "COMPONENT_DEFAULT"`, `componentId`, `componentName` 을 담는다. 화면은 「구성요소 Compute 담당자로 자동 지정 — soon.park」으로 보여 준다.

### 4.4 보관·삭제
- 보관: 새로 붙일 수 없다(피커에서 빠짐). 이미 붙은 이슈에는 그대로 보이고, 필터에는 「보관됨」 묶음으로 남는다. 자동 지정에도 쓰지 않는다. 복원할 수 있다.
- 삭제: 확인 창에 영향 이슈 수를 보여 주고, 지우면 붙어 있던 이슈에서 빠지며 이슈마다 `COMPONENTS_CHANGED` 제거 기록을 남긴다(라벨 삭제와 같은 방식).
- 지난 기록은 **당시 이름**을 보여 준다 — 라벨 기록과 같은 방식(기록에 id·당시 이름 저장, 화면은 저장된 이름 그대로). 이름을 바꿔도 지난 기록은 그대로다(내 판단, 빌더 점검 반영).

### 4.5 변경 기록
- 새 이력 유형 `COMPONENTS_CHANGED` — payload `{added:[{id,name}], removed:[...]}`. 차이가 없으면 남기지 않는다. 라벨 `LABELS_CHANGED` 와 같은 모양.

## 5. API

- `GET/POST /api/v1/projects/{key}/components`, `PATCH /{id}` (이름·설명·담당자·보관 여부), `GET /{id}/issue-count`, `DELETE /{id}`.
  - 응답 `ComponentResponse { id, name, description, defaultAssignee: UserSummary|null, defaultAssigneeValid: boolean, archived: boolean, issueCount }`.
- `PUT /api/v1/projects/{key}/issues/{number}/components` — 전체 교체(`{ componentIds: [...] }`). 보관된 id 를 새로 넣으면 400, 이미 붙어 있던 보관 id 는 유지 허용.
- `CreateIssueRequest.componentIds` 추가. 서버가 4.3 규칙으로 자동 지정.
- `IssueResponse.components: ComponentSummary[] { id, name, archived }` (목록 순서).
- 검색 필터 `component` — id 또는 이름 CSV, 고른 것 중 **하나라도** 붙은 이슈(OR). 특수 값 `none` = 구성요소 없음. 기존 「미지정」 필터 토큰 관례가 있으면 그것을 따른다.
- 오류 코드는 기존 라벨·관계 API 의 `errors.code` 관례를 따른다(예: `COMPONENT_NAME_TAKEN`, `COMPONENT_ARCHIVED`, `COMPONENT_ASSIGNEE_INVALID`, `PERSONAL_PROJECT_UNSUPPORTED`).

## 6. 화면 (비주얼 컴패니언 시안으로 사용자 승인)

**보이는 조건**: 프로젝트에 사용 중(보관 안 됨) 구성요소가 하나도 없으면 이슈 상세·만들기·필터·열 고르기에서 구성요소를 **숨긴다**. 단, 보관된 구성요소가 붙은 이슈의 상세에서는 그 값만 읽기 전용으로 보인다.

- **이슈 상세 속성 영역**: 첫 묶음의 **담당자 바로 아래** 「구성요소」 행 — 칩 목록 + 「＋」 피커(여러 개 선택, 검색). 사용자가 A 안 선택(Jira·Redmine·YouTrack 모두 담당자 근처에 항상 보이는 칸).
- **이슈 만들기**: 데스크톱 만들기 창에 「구성요소」 다중 선택을 우선순위 근처에 둔다. 고르면 아래에 「만들면 Compute 담당 soon.park 님이 맡아요」 안내(데스크톱 창에는 담당자 칸이 없어 항상 자동 지정). 모바일 만들기 시트는 담당자를 이미 골랐으면 안내를 숨긴다.
- **필터**: 필터 바·모바일 필터 시트에 「구성요소」 facet(목록 순서, 「구성요소 없음」 — 다른 facet 처럼 이슈 수는 보이지 않는다(내 판단, 빌더 점검 반영), 보관된 것은 아래 「보관됨」). URL·저장된 뷰에 `component` 로 남는다. 「필터 모두 지우기」에 포함.
- **목록**: 열 고르기에 선택 열 「구성요소」(기본 꺼짐) — 칩 2개 + 「+N」.
- **보드 카드·모바일 행**: 라벨 칩 앞에 구성요소 칩을 작게(최대 2개 + 「+N」).
- **활동 기록**: 구성요소 추가·제거, 자동 지정 문구.
- **프로젝트 설정**: 「라벨」 아래 「구성요소」 섹션 — 표(이름·설명·담당자·이슈 수·편집/보관), 「＋ 구성요소 추가」, 「보관한 구성요소 N개 보기」 접기. 비어 있으면 「영역별로 이슈를 나누고 영역 담당자를 자동으로 붙여요. 구성요소를 추가하면 이슈에 칸이 생겨요.」 안내. 추가·편집은 대화창(이름·설명·담당자 피커). OWNER/ADMIN 이 아니면 읽기 전용.
- 디자인 시스템(`docs/design-system/`) 토큰만 쓴다. 구현 뒤 실제 화면 캡처로 사용자 승인을 받는다.

## 7. MCP · AI 비서

- `get_project`: 응답에 `components: [{ name, assignee, archived }]` (보관된 것 포함, 표시).
- `list_issues`: `component` 인자(이름 CSV, 하나라도 일치, `none` 지원).
- `create_issue` / `update_issue`: `components: string[]` (이름, update 는 전체 교체). 목록에 없는 이름은 **만들지 않고** 실패(라벨과 다름) — 쓰기 전에 거부.
- `get_issue_detail` / 목록 보기 응답에 구성요소 이름.
- 기본 연결 도구 설명 상한 `DEFINITION_TOKEN_CAP` 를 16,700 → **약 16,850** 으로 올린다(사용자 승인 2026-10-25). 실제 필요한 만큼만 올리고 날짜 주석을 남긴다. 앱별 도구 수 상한(18)은 그대로 — 새 도구를 만들지 않는다.
- AI 비서 시스템 프롬프트(`assistant-system-prompt.ts`)의 필터 안내에 「구성요소 → component」 한 줄 추가.
- 플러그인 버전 0.1.12.

## 8. 가져오기 API (WP-883 확장)

- `ImportIssueRequest.componentNames: string[]` — 이름(대소문자 무시)으로 찾는다. **보관된 구성요소도 허용**(지난 기록). 없는 이름은 `IMPORT_UNKNOWN_COMPONENTS` 로 거부, 쓰기 전에 검증.
- `history[]` 에 `COMPONENTS_CHANGED` 허용 — `added`/`removed` 는 구성요소 이름, 같은 규칙으로 검증.
- 가져오기는 자동 지정을 하지 않는다.
- 구성요소 자체를 만드는 가져오기 엔드포인트는 두지 않는다 — 이관 스크립트가 먼저 일반 API 로 12개를 담당자와 함께 만든다.
- `docs/integrations/issue-import-api.md` 의 요청 필드·history 유형·오류 표·준비 순서·CLIM 주의를 갱신한다.

## 9. 테스트

- API: 통합 테스트 — 관리 권한(OWNER/ADMIN/멤버/비멤버), 개인 프로젝트 거부, 이름 중복(대소문자), 보관 id 새로 붙이기 거부, 자동 지정(담당자 있음/없음/여러 구성요소/담당자 비활성·비멤버/AI 제외/가져오기 제외), 알림·이벤트, 이력 기록, 삭제 시 제거 기록, 필터(OR·none·이름·보관), 가져오기(이름·보관 허용·없는 이름 거부·history).
- web: 순수 로직 vitest(필터 파싱·직렬화, 자동 지정 안내 문구 판정, 보이는 조건 판정), 컴포넌트 테스트(권한별 설정 버튼), E2E(설정 추가→상세 피커→필터 URL·요청, 만들기 창 안내·payload, 구성요소 없는 프로젝트에서 숨김).
- MCP: 스키마 스냅샷·토큰 상한 테스트, 이름 해석(없는 이름 실패).

## 10. 배포 순서

API(V218) → ai-agent·MCP → web. 웹은 `IssueResponse.components`·`/components` API 에 의존한다. 플러그인 태그 `genia-works--v0.1.12` 는 web 과 같이 또는 먼저.

## 11. 빌더에게 맡기는 것

- 클래스·파일 이름, 저장소 쿼리 모양, 피커 컴포넌트 재사용 방식(LabelPickerPopover 를 일반화할지 새로 만들지).
- 필터 facet 의 「보관됨」 묶음 표현.
- 오류 코드 이름의 최종 철자.
