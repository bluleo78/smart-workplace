# WP-888 버전(수정 버전·영향 버전) 설계

- 이슈: WP-888 「사용자로서 한 이슈에 수정 버전·영향 버전을 여러 개 지정하고 버전별로 모아 보고 싶다」 (에픽 WP-882 Jira 이관, 웨이브 5)
- 작성: 2026-10-26
- 「(내 판단)」 표시는 대화에서 사용자가 정하지 않아 설계자가 정한 것이다. 사용자는 2026-10-26 전체 규칙 목록을 보고 「좋아」로 승인했다.

## 1. 왜 만드는가

Jira CLIM 은 수정 버전(fixVersion) 151건 중 7건이 두 버전 이상에 걸친다(v1.5.x·v1.6.x 를 함께 유지해 백포트 결함이 여러 버전에 나간다). 영향 버전(affectsVersion)도 12건 있다. Works 의 마일스톤은 이슈당 하나이고 날짜가 필수라 이 정보를 담지 못한다.

팀장은 버전 화면을 자주 연다 — **그 버전에 어떤 이슈·기능이 나가는지 파악하고 진행 상태를 확인**하려고(사용자 발언). Jira 의 Releases 개념을 참고해 만든다(사용자 요청).

## 2. 목표 · 비목표

**목표**
- 프로젝트마다 버전 목록(이름·설명·시작일·출시일·상태)을 두고, 프로젝트 머리의 「버전」 화면에서 관리한다.
- 이슈에 **수정 버전**과 **영향 버전**을 각각 여러 개 붙인다.
- 버전 상세에서 그 버전에 나가는 이슈를 **이슈 유형별로 묶어** 보고(사용자 결정), 수정 버전 기준 진행 막대를 본다.
- Jira 처럼 「출시」 동작 — 끝나지 않은 이슈를 다음 버전으로 옮길 수 있다.
- 출시일이 있는 버전을 타임라인에 ▲ 로 마일스톤 ◆ 과 함께 보인다(사용자 선택 2번).
- 목록·저장된 뷰·모바일에서 수정 버전·영향 버전으로 걸러 본다.
- MCP·AI 비서가 버전으로 찾고, 붙이고, 목록을 읽는다.
- 가져오기 API 가 버전과 그 변경 이력을 원본대로 넣는다.

**비목표**
- 마일스톤 변경. 마일스톤은 지금 그대로(이슈당 하나) 둔다 — 사용자 결정(B안). **마일스톤과 버전 사이에 연결 데이터는 없다**(사용자 선택 2번: 독립 + 타임라인에 함께 표시).
- 버전 순서 끌기, 버전 합치기, 빌드·배포 연동, 출시 알림, 릴리스 노트 내보내기(내 판단, 사용자 확인).
- 버전 관리 MCP 도구(앱별 도구 수 상한 18).
- 만들기 대화상자의 버전 칸(내 판단, 사용자 확인 — 상세에서 붙인다).
- 개인 프로젝트 지원 — 구성요소와 같은 이유(내 판단). 서버 400 `PERSONAL_PROJECT_UNSUPPORTED`, 화면은 「버전」 버튼을 그리지 않는다.

**하면 실패인 것**
- 버전을 쓰지 않는 기존 프로젝트의 이슈 상세·필터·열·타임라인이 바뀐다(빈 칸·빈 필터).
- 영향 버전 이슈가 진행률에 섞인다.
- 마일스톤 기능(진행률·타임라인 ◆·`milestone` 필터·MCP `milestoneId`)이 회귀한다.

## 3. 데이터

새 마이그레이션 `V219__project_versions.sql` (머지 직전 main 번호와 다시 대조한다).

`project_version`
- `id`, `tenant_id`, `project_id` (FK project, cascade)
- `name VARCHAR(40)` — 프로젝트 안에서 대소문자 무시 유일(`UNIQUE (project_id, lower(name))`)
- `description VARCHAR(500)` null 가능
- `start_date DATE`, `release_date DATE` 둘 다 null 가능. 둘 다 있으면 `start_date <= release_date`
- `released_at TIMESTAMPTZ` null = 미출시. `archived_at TIMESTAMPTZ` null = 사용 중. 상태는 이 둘에서 나온다: 보관 > 출시됨 > 미출시
- `created_by` FK user SET NULL, `created_at`, `updated_at`

`issue_version`
- PK `(issue_id, version_id, kind)`, `kind` ∈ `FIX`, `AFFECTS` (CHECK). 두 FK 모두 cascade, `tenant_id`, `created_at`
- 인덱스 `(version_id, kind)` — 필터·집계용
- 한 이슈에 같은 버전을 수정·영향으로 동시에 붙일 수 있다(Jira 와 같음).

두 표 모두 구성요소(V218)처럼 `tenant_id` + 행 수준 보안 정책. `TenantPurgePlan` 에 `issue_version` → `project_version` 순서로 추가.

**프로젝트당 최대 200개**(보관 포함), 이름 1~40자, NFC 정규화(구성요소 `SingleLineTitles` 와 같은 방식).

**목록 순서**(화면·피커·필터·MCP 모두, 내 판단): 미출시 → 출시됨 → 보관. 미출시는 출시일 오름차순(날짜 없는 것은 뒤, 같으면 이름), 출시됨·보관은 출시일 내림차순(없으면 `released_at` 내림차순), 마지막으로 이름(대소문자 무시). 끌어서 바꾸지 않는다.

## 4. 규칙

### 4.1 권한
- 보기(목록·상세·이슈 수): 프로젝트를 읽을 수 있는 사람.
- 만들기·편집·출시·출시 취소·보관·복원·삭제: **프로젝트 OWNER** 와 테넌트 ADMIN — 구성요소와 같음.
- 이슈에 붙이기·떼기: 라벨·구성요소와 같은 멤버 권한.

### 4.2 상태
- 미출시 버전, 출시됨 버전 모두 새로 붙일 수 있다 — 출시 뒤 「이 버전에서 난 결함」(영향 버전)을 다는 일이 흔하다(Jira 와 같음).
- 보관: 새로 붙일 수 없다(피커에서 빠짐). 이미 붙은 값은 유지되고 흐린 점선 칩 「(보관됨)」으로 보인다(구성요소와 같은 모양). 필터에는 「보관됨」 묶음으로 남는다. 타임라인에는 그리지 않는다. 복원할 수 있다.
- 출시 취소: 미출시로 돌아간다(`released_at` 비움). 출시일(`release_date`)은 남긴다.

### 4.3 출시
- `POST .../versions/{id}/release` `{ releaseDate?: date, moveUnresolvedTo?: versionId }`.
  - `releaseDate` 를 주지 않으면 기존 출시일, 그것도 없으면 오늘(테넌트 기준 Asia/Seoul).
  - `moveUnresolvedTo` 가 있으면: 이 버전을 **수정 버전**으로 가진 이슈 중 상태 범주가 완료·취소가 아닌 것에서 이 버전을 빼고 대상 버전을 넣는다(이미 있으면 빼기만). 대상은 같은 프로젝트의 미출시·보관 아님 버전이어야 하고 자기 자신이면 400. 영향 버전은 건드리지 않는다.
  - 옮긴 이슈마다 `FIX_VERSIONS_CHANGED` 이력을 남긴다. 이벤트는 구성요소·라벨·마일스톤 같은 정리성 변경과 같은 `updatedWithoutTouch` 경로 — AI 담당 이슈를 옮겨도 AI 작업이 시작되지 않는다(내 판단, 빌더 점검 반영).
- 화면 대화상자: 출시일(기본 위 규칙), 끝나지 않은 이슈가 있으면 「다음 버전으로 옮기기 [미출시 버전 선택, 기본 = 목록 순서상 다음 미출시]」 / 「그대로 두기」(옮길 미출시 버전이 없으면 「그대로 두기」만).

### 4.4 삭제
- 보관한 버전만 지울 수 있다. 화면은 보관된 행에만 삭제를 보이고, **서버도** 보관 안 된 버전 삭제를 400 `VERSION_NOT_ARCHIVED` 로 막는다 — 구성요소는 화면에서만 막으므로 이것은 버전에 새로 두는 서버 규칙이다(내 판단).
- `DELETE .../versions/{id}?moveTo={versionId}` — `moveTo` 가 있으면 붙어 있던 이슈의 같은 종류(수정→수정, 영향→영향)로 옮기고, 없으면 떼기만. 이슈마다 해당 종류 변경 이력을 남긴다.
- 확인 창에 수정·영향 이슈 수를 보여 주고 「다른 버전으로 옮기기 / 떼기」를 고른다.

### 4.5 변경 기록
- 새 이력 유형 두 가지: `FIX_VERSIONS_CHANGED`, `AFFECTS_VERSIONS_CHANGED` — payload `{added:[{id,name}], removed:[...]}`, 차이 없으면 남기지 않음. 지난 기록은 당시 이름을 보인다(구성요소 `COMPONENTS_CHANGED` 와 같은 방식).

### 4.6 동시성
- 모든 경로가 **이슈 행 → 버전 행** 한 방향으로만 잠근다(내 판단, 빌더 점검 반영 — 두 방향이 섞이면 교착).
  - 교체·이슈 만들기·가져오기: 이슈 행 `FOR UPDATE` → 관련 버전 행 공유 잠금(구성요소와 같음).
  - 출시 옮기기·삭제: 대상 이슈 id 를 먼저 읽고, 그 이슈 행들을 id 순으로 `FOR UPDATE` → 원래·대상 버전 행을 id 순으로 잠근 뒤, 잠근 상태에서 대상 이슈 집합을 다시 확인해 그 사이 바뀐 것을 반영한다.

## 5. API

- `GET/POST /api/v1/projects/{key}/versions`, `GET/PATCH/DELETE /{id}`, `POST /{id}/release`, `POST /{id}/unrelease`. PATCH 는 이름·설명·시작일·출시일·보관 여부.
  - `VersionResponse { id, name, description, startDate, releaseDate, status: UNRELEASED|RELEASED|ARCHIVED, releasedAt, progress: { done, inProgress, todo }, affectsCount }`. `progress` 는 수정 버전 이슈를 상태 범주로 센 것 — **취소는 완료로 센다**. 사이클 진행(`CycleProgress`, WP-243)과 Jira(취소도 완료 범주)와 같다(내 판단, 빌더 점검 반영). 「완료/전체」의 전체 = done+inProgress+todo = 수정 버전 이슈 전체, 탭 개수도 같은 수(취소 이슈도 보이고 센다). `affectsCount` 는 영향 버전 이슈 전체 수(취소 포함).
  - 버전 만들기 REST 는 개인 API 토큰(`swp_`)으로 부를 수 있다 — 이관 스크립트가 쓴다.
- `PUT /api/v1/projects/{key}/issues/{number}/versions` — `{ fixVersionIds: [...], affectsVersionIds: [...] }` 둘 다 전체 교체(빠진 키는 그 종류를 그대로 둔다). 보관된 id 를 새로 넣으면 400, 이미 붙어 있던 보관 id 유지는 허용.
- `IssueResponse.fixVersions`, `IssueResponse.affectsVersions`: `VersionSummary[] { id, name, status }` (목록 순서).
- 검색 필터 `fixVersion`, `affectsVersion` — id 또는 이름 CSV, OR, 특수 값 `none`. 구성요소 `component` 필터와 같은 해석 규칙.
- 버전 상세 화면이 쓰는 이슈 목록은 기존 검색 API 에 `fixVersion=<id>` / `affectsVersion=<id>` 를 걸어 가져온다(새 목록 API 를 만들지 않는다, 내 판단).
- 오류 코드는 구성요소 관례: `VERSION_NAME_TAKEN`, `VERSION_ARCHIVED`, `VERSION_NOT_FOUND`, `VERSION_NOT_ARCHIVED`, `VERSION_LIMIT_EXCEEDED`, `VERSION_INVALID_DATES`, `VERSION_MOVE_TARGET_INVALID`, `PERSONAL_PROJECT_UNSUPPORTED`.
- 실시간: 버전 목록 변경 이벤트를 구성요소처럼 publish 하고 web `resourceInvalidation` 규칙을 둔다.

## 6. 화면 (비주얼 컴패니언 시안으로 사용자 승인)

**보이는 조건**: 프로젝트에 보관 안 된 버전이 하나도 없으면 이슈 상세의 두 줄·필터·열·타임라인 ▲ 를 **숨긴다**. 보관된 버전이 붙은 이슈의 상세에서는 그 값만 읽기 전용으로 보인다. 프로젝트 머리의 「버전」 버튼은 버전이 없어도 보인다(첫 버전을 거기서 만든다, 내 판단).

- **프로젝트 머리**: 사이클 · **버전** · 타임라인 · 설정 순서. 모바일은 ⋯ 메뉴에 같은 순서.
- **버전 목록** `/projects/{key}/versions`: 「미출시 N · 출시됨 N」 요약, 「＋ 버전 만들기」(OWNER/ADMIN), 표(이름·상태 배지·진행 막대와 「완료/전체」·시작일·출시일 — 미출시인데 출시일이 지났으면 붉은 「지남」·⋯ 메뉴: 편집·출시/출시 취소·보관/복원·삭제(보관된 행만)). 보관한 버전은 「보관한 버전 N개 보기」 접기. 비어 있으면 「출시 단위로 이슈를 모으고 진행을 봐요. 버전을 만들면 이슈에 수정 버전·영향 버전 칸이 생겨요.」 안내. 모바일은 표 대신 카드 목록.
- **버전 상세** `/projects/{key}/versions/{id}`: 머리(이름·상태·기간 「N일 남음/지남」·설명·[편집][출시]), 진행 막대(완료·진행 중·할 일, 수정 버전 기준), 「영향 버전으로 붙은 결함 N건」. 탭 「이 버전에 나가는 것 N」(수정 버전) / 「이 버전에서 난 결함 N」(영향 버전). 각 탭은 이슈를 **이슈 유형별로 묶고**(유형 순서는 프로젝트 유형 순서), 행에 상태 아이콘·키·제목·상태·담당자. 다른 버전에도 수정 버전으로 붙은 이슈는 「v1.5.3 에도 포함」을 덧붙인다. 「이슈 목록에서 열기」 → 이슈 목록에 `fixVersion`(또는 `affectsVersion`) 필터를 건 URL.
- **출시 대화상자**·**만들기/편집 대화상자**(이름·설명·시작일·출시일)·**삭제 확인**(4.4).
- **이슈 상세 속성 영역**: 구성요소 아래 「수정 버전」, 「영향 버전」 두 줄 — 칩 + 「＋」 피커(여러 개, 검색, 미출시 먼저). 칩을 누르면 버전 상세로.
- **필터**: 필터 바·모바일 필터 시트에 「수정 버전」, 「영향 버전」 facet(목록 순서, 「없음」, 보관된 것은 「보관됨」 묶음). URL·저장된 뷰에 남고 「필터 모두 지우기」에 포함.
- **목록 열**: 열 고르기에 「수정 버전」, 「영향 버전」(기본 꺼짐) — 칩 2개 + 「+N」.
- **보드 카드·모바일 행**: 넣지 않는다(내 판단 — 카드가 이미 구성요소·라벨 칩으로 차 있다).
- **타임라인**: 지금 마일스톤은 맨 위 「마일스톤」 레인에 이름 칩(Diamond 아이콘)과 세로 점선으로 그려진다. 버전은 그 아래 **별도 「버전」 레인**에 이름 칩(▲ 아이콘, 다른 색)과 세로 점선(다른 색)으로 그린다 — 마일스톤 레인의 빈 곳 클릭(마일스톤 만들기)·겹침 배치와 섞이지 않게(내 판단, 빌더 점검 반영). 버전 레인은 빈 곳 클릭 동작이 없고, 칩을 누르면 버전 상세로 간다. 칩 겹침 배치는 마일스톤 배치 로직을 재사용한다. 출시일 있는 미출시·출시됨 버전만, 하나도 없으면 레인을 그리지 않는다. 모바일 일정 목록에 「버전 N」 칩(마일스톤 칩과 같은 방식). 실제 캡처 승인 때 사용자가 확인한다.
- **활동 기록**: 수정·영향 버전 추가·제거.
- 디자인 시스템 토큰만 쓴다. 구현 뒤 실제 화면 캡처로 사용자 승인을 받는다.
- AI 화면 컨텍스트: 버전 상세 화면은 `useRegisterAiScreenContext` 로 버전 이름·상태를 등록한다.

## 7. MCP · AI 비서

- `get_project`: `versions: [{ name, status, releaseDate }]` 추가(보관 포함). 롤링 배포 대비 실패해도 나머지를 돌려준다(구성요소 `.catch` 와 같음).
- `list_issues`: `fixVersion`, `affectsVersion` 인자(이름 CSV, OR, `none`).
- `create_issue` / `update_issue`: `fixVersions`, `affectsVersions: string[]`(이름, update 는 종류별 전체 교체). 없는 이름은 만들지 않고 쓰기 전에 실패. update 는 이미 붙은 보관 버전 이름만 허용.
- `get_issue_detail`·목록 보기 응답에 두 종류 버전 이름.
- 도구 수는 그대로. 인자 설명이 늘어 `DEFINITION_TOKEN_CAP`(현재 16,900)를 넘으면 **올리기 전에 사용자에게 묻는다**.
- AI 비서 시스템 프롬프트 필터 안내에 「수정 버전 → fixVersion, 영향 버전 → affectsVersion」.
- 플러그인 버전 0.1.14(main 이 0.1.13 태그까지 나갔다), `marketplace.json` 참조도 같이.

## 8. 가져오기 API (WP-883 확장)

- `ImportIssueRequest.fixVersionNames`, `affectsVersionNames: string[]` — 대소문자 무시로 찾는다. **보관·출시 버전 모두 허용**. 없는 이름은 `IMPORT_UNKNOWN_VERSIONS` 로 쓰기 전에 거부. 같은 이름 중복은 하나로.
- `history[]` 에 `FIX_VERSIONS_CHANGED`, `AFFECTS_VERSIONS_CHANGED` 허용 — `added`/`removed` 는 이름.
- 버전을 만드는 가져오기 엔드포인트는 두지 않는다 — 이관 스크립트가 먼저 버전 API 로 만들고(출시된 것은 출시까지), 그다음 이슈를 가져온다.
- Jira 이력에만 나오고 지금은 지워진 버전 이름도 프로젝트에 있어야 받는다(구성요소와 같음). 이관 스크립트는 그런 이름을 **보관된 버전**으로 먼저 만들어 둔다 — 이 준비 순서를 문서에 적는다(내 판단).
- 버전 상세의 이슈 목록은 검색 API 한 페이지 상한(100)을 넘을 수 있어 커서로 끝까지 읽는다.
- `docs/integrations/issue-import-api.md` 갱신(요청 필드·history 유형·오류·준비 순서·CLIM 주의).

## 9. 테스트

- API 통합: 권한(OWNER/ADMIN/멤버/비멤버), 개인 프로젝트 거부, 이름 중복(대소문자)·날짜 순서·상한, 상태 전이(출시·취소·보관·복원), 출시 옮기기(완료·취소 제외, 영향 버전 불변, 대상 검증, 이력), 삭제(보관만, 옮기기/떼기, 종류 유지, 이력), 교체(보관 id 새로 거부·유지 허용), progress 집계(영향 제외), 필터(OR·none·이름·보관·두 필터 AND), 가져오기(이름·보관 허용·없는 이름 거부·history), 동시 교체 경합.
- web: vitest(필터 파싱·직렬화, 목록 순서, 상태·「지남」 판정, 유형별 묶기, 보이는 조건), 컴포넌트(권한별 버튼), E2E(버전 만들기→상세 피커→필터 URL·요청, 버전 상세 탭·유형 묶음, 출시 대화상자 payload, 타임라인 ▲ 클릭, 버전 없는 프로젝트 숨김).
- MCP: 스키마 스냅샷·토큰 상한, 이름 해석(없는 이름 실패, 보관 규칙).

## 10. 배포 순서

API(V219) → ai-agent·MCP → web. 웹은 `IssueResponse.fixVersions/affectsVersions`·`/versions` API 에 의존한다. 플러그인 태그 `genia-works--v0.1.14` 는 web 과 같이 또는 먼저.
